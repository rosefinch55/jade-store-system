### 6.5 同日第二轮：一个认证绕过 + 三项收口（#54–#57）

**#54 鉴权失败后身份留在 Tomcat 线程上，下一个不带令牌的请求被当成那个人处理（最严重）**。机理：`AuthInterceptor.preHandle` 校验不过时抛异常，Spring 的 `HandlerExecutionChain.interceptorIndex` 还停在 -1，本拦截器的 `afterCompletion`（`CurrentUser.clear()` 在那儿）不会被回调，`ThreadLocal` 里的身份留在该线程；同一条 keep-alive 连接的下一个请求拿到的就是别人的身份。实测数据（`tools/auth-leak-probe.js`，只发 GET）：老 jar **12 轮里 10 轮**命中，裸打的 `/api/auth/me` 直接返回 `lishifuyudiao`（id=4）的资料，`/api/sales` 也放行；新 jar **0/12**。22 项安全回归抓不到它，因为它测的是单发请求的令牌/越权，不测「一次失败之后的下一个请求」。修法是所有拒绝走 `deny()`：在里面自己清 `CurrentUser`、顺手留痕，再把异常交回 `GlobalExceptionHandler`。

### 6.6 当天门店追加的两条（#59 #60）

**#59 加工任务逾期要能催**。店里的原话是「加工过期了怎么办？不得说逾期了去催吗」。原来任务列表只有「期限」一列，过期与没过期长得一模一样，老板得自己对着日期算——而库里 204 条任务有 **111 条已过期限**（待加工 33、在加工 78），界面上一个提示都没有。现在：

- 「逾期」是**派生态**，口径 `status ∈ {待加工, 在加工}` 且 `deadline < 今天`。待交付、已交付不算：货已经在师傅手上交完或已回店，再标逾期只会误导。没有存一个 `status='已逾期'`，因为过一天要批量刷库、老板改状态时还得记得回滚，两处都会错。
- 列表返回 `overdue` / `overdueDays`；「只看逾期」的筛选**在分页前**下推成 SQL 条件（跟分期管理里逾期筛选同一个写法，`SaleController:340-345`），另发一次 `selectCount` 供表头「共 N 个任务 · 逾期 M 个待催」计数，不受翻页影响。
- 催办 `POST /api/process-tasks/{id}/urge` 只写 `urge_count` 和 `last_urge_at`，师傅端任务卡显示「门店已催办 N 次（时间）」。**不做推送**：没有可用的对外消息通道（微信模板消息要备案域名，见 AGENTS.md §七第 5 条），真催人还是打电话。落库的只有「催过没有、催了几次、什么时候」。
- 该催的口径之外一律拦：状态是待交付/已交付 → 409；还没到期 → 422；未登录 → 401。

**#60 上门预约时段改成结构化时间（一次 schema 变更）**。`t_visit_appt.expect_slot VARCHAR(64)` 存的是「2026-10-25 下午」这种自由文本，`specs/006-processing` 早就把它列为差异一：没法做区间比对，只能按字符串相等判重，「下午 2-4 点」和「下午 3-5 点」算不冲突，全靠老板人工协调。按店里「一次只接待一位」的实际做法拆列：

| | 改前 | 改后 |
|---|---|---|
| 列 | `expect_slot VARCHAR(64)` | `expect_date DATE` + `start_time TIME` + `end_time TIME` |
| 一次交接占多久 | 说不清 | 固定一小时，`end_time` 服务端算，客户端传了也不算 |
| 可选范围 | 任意文本 | 今天起 14 天内；起点限 10:00–19:00 的整点或半点 |
| 冲突判定 | 字符串完全相等 | 区间重叠 `from < 已有.end && 已有.start < to`，并与客户到店预约（`t_reservation.expect_slot` 本就是 DATETIME）同区间互斥 |
| 并发重复 | 无防护 | 函数唯一索引 `uk_visit_slot_open` 挡整段相同的并发提交（1062 转 409） |

改表时 `t_visit_appt` 是 **0 行**，所以不涉及历史值换算；`docs/upgrade-20261026.sql` 里仍留了一段模板 UPDATE 与预检查询，供真有数据的库重放。改动面：实体、创建接口（含校验与区间判重）、经营日历（原来靠 `parseLoose` 猜文本，现在直接读列，那段兜底代码删掉）、管理端上门预约列表、外部端表单（`step=1800` 半小时步进 + 前置校验）、停工中的小程序页面（保持与接口对得上）。

残留一条，写进了 spec 差异一：区间重叠在服务层判，两个并发请求若约**部分重叠但不完全相同**的时段（同一分钟内并发提交 10:00 与 10:30），唯一索引挡不住。同一往来方在同一分钟内并发约相邻时段的概率极低，且老板确认环节还能挡一道，暂不为它加表锁。
