# 任务清单：加工与上门

## 阶段一：数据补全

- [ ] **T001 造完工交付与上门预约数据**
  `t_delivery_apply`、`t_delivery_image`、`t_visit_appt` 三张表为空。需要：
  - 从「待交付」状态的 204 条任务里挑 15 条造交付申请（10 条待确认、5 条已确认）
  - 每条申请配 3 张过程图（可用占位路径 `/upload/delivery/xxx.jpg`，前端显示时容错）
  - 造 8 条上门预约（5 条待上门、2 条已完成、1 条已取消），关联已确认的交付申请
  
  *验收*：三张表都有数据；`SELECT status, COUNT(*) FROM t_delivery_apply GROUP BY status` 两态都有。

- [ ] **T002 给师傅账号关联档案**
  现有 2 个账号（admin、sale01），没有师傅账号。按 `craftsman_{id}` 约定建 2 个：`craftsman_37`（李师傅玉雕）、`craftsman_38`（张师傅切料），密码同 `123456`。
  *验收*：用 `craftsman_37` 登录，任务列表只显示李师傅的。

## 阶段二：后端师傅端

- [ ] **T003 师傅任务列表 `GET /api/craftsman/tasks`**
  从用户名解析出 `craftsman_id`，只查自己的任务。
  *验收*：AC-01、AC-02 通过。

- [ ] **T004 提交完工 `POST /api/craftsman/tasks/{id}/delivery`**
  状态须「在加工」、无待确认申请、三阶段图齐全；事务改任务状态为「待交付」。
  *验收*：AC-03、AC-04、AC-05 通过。

## 阶段三：后端老板端

- [ ] **T005 任务管理 `GET /api/process-tasks`**
  全部任务，按师傅、状态、期限筛选；销售只读。`overdueOnly=true` 只看逾期（派生态，口径见 spec FR-017），响应带 `overdueCount`；配套 `POST /api/process-tasks/{id}/urge` 记催办。
  *验收*：能按师傅筛出 41 条；勾「只看逾期」总数与列表一致。

- [ ] **T006 开始加工 `POST /api/process-tasks/{id}/start`**
  待加工 → 在加工。
  *验收*：状态不对返回 409。

- [ ] **T007 确认完工 `POST /api/delivery-applies/{id}/confirm`**
  接受则申请「已确认」、任务「已交付」；拒绝则任务退回「在加工」，可重新提交。
  *验收*：拒绝后该任务能再次提交完工。

- [ ] **T008 上门预约 `POST /api/visit-appts`**
  两个关联 id 二选一；出让申请须「已通过」、交付申请须「已确认」；时段按区间重叠判重（2026-10-26 起日期与起止时间结构化）。
  *验收*：AC-06、AC-07、AC-08 通过。

- [ ] **T009 预约确认与取消**
  `POST /api/visit-appts/{id}/confirm`（改「已完成」）、`/cancel`（改「已取消」并释放时段）。
  *验收*：取消后同时段可再约。

## 与其他 feature 的交界

- **与 `004-transfer`**：上门预约的另一个来源是「已通过的出让申请」，`transfer_apply_id` 指向那张表
- **与 `001-goods`**：加工完工的货品按「加工完工」来源建档，任务挂在货品上；确认交付后仍走 UC-02 入库
- **与 `002-sale`**：工费结算走货款记录（`biz_type='加工工费'`），不在本 feature 做
