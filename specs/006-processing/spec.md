# 功能规格：加工与上门

**功能分支**：`006-processing`
**需求来源**：分析设计文档 §2.3 UC-15 预约上门时间、UC-16 查看加工任务、UC-17 提交完工交付申请
**依赖**：`000-base`（外部账号与权限）、`004-transfer`（出让申请）、`001-goods`（加工完工入库）
**状态**：Draft

## 范围

加工任务的查看、完工交付申请、上门交接预约。

任务的**创建**不在本 feature——老板在安排加工时生成 `t_process_task`，属于 `001-goods` 建档时的一步（加工完工来源的货品）。本处只做师傅侧的三件事：看任务、报完工、约上门。

## 三个角色，一条链

```
老板安排加工（004/001）
      ↓ 生成 t_process_task（待加工 → 在加工）
加工师傅看任务（UC-16）
      ↓ 完工后提交申请（UC-17）
状态变「待交付」，生成 t_delivery_apply（待确认）
      ↓ 老板确认
师傅预约上门交货（UC-15）→ 生成 t_visit_appt
      ↓ 上门交接
老板按 UC-02 建档入库（加工完工来源）
```

## 性能与约束

- 任务查询 2 秒内反馈（UC-16）
- 完工提交后 1 秒内反馈（UC-17）
- 上门预约提交后 1 秒内反馈，不超过 3 次操作（UC-15）
- 师傅与内部账号共用登录入口，登录后只见任务相关功能（UC-16 设计约束）

## 边界情况

- 一条任务交付后若返工，由老板重新派工生成新任务，原任务保留「已交付」
- 上门预约取消后时段释放，可被他人预约
- 供应商的上门事项只能是出让交货；加工师傅的只能是完工交付，系统按角色限制可选项
- 老板也可代师傅提交完工申请（报告 §4.4 说老板对全用例有代执行权限）

## 与文档的差异

**一、上门时段无法精确判冲突 —— 已消除（2026-10-26 走了一次 schema 变更）**

原来 `t_visit_appt.expect_slot` 是 `VARCHAR(64)` 的自由文本，UC-15 规则②「同一时段只安排一次上门交接」只能按字符串相等判重，写法不同就不算冲突，实际靠老板人工协调。

现在拆成 `expect_date DATE` + `start_time TIME` + `end_time TIME`（见 `docs/upgrade-20261026.sql`）：时段口径定为「一次交接占一小时，起时间在 10:00–19:00 之间、按整点或半点选」，`end_time` 由服务端算，不接受客户端传值。判重改成区间重叠（同日 `from < 已有.end && 已有.start < to`），与数据库函数唯一索引（整段完全相同 + 状态待上门）形成两层防护；与客户到店预约的互斥也用同一区间的 `BETWEEN` 比对，不再需要手工 parse 文本。

残留一条：区间重叠的判重在服务层做，两个并发请求若时段部分重叠（非整段相同），数据库唯一索引拦不住，理论上仍可能双双通过。同一往来方在同一分钟内并发约两个相邻时段的概率极低，且老板确认环节还能挡一道，暂不加表锁。

**二、过程图只有一张表**

UC-17 要求加工前、加工中、完工三类图，`t_delivery_image` 需要有个字段区分类型。查表结构确认有 `stage` 或类似字段则直接用，没有就加——见 `data-model.md` 的说明。

**补充（2026-10-26 复核，对应代码审查报告 §三 B 组）**

B10｜老板不能代师傅提交完工。规格边界写了老板可代提交，实现的角色门槛只放 CRAFTSMAN。处置：接受实现（代提交会把责任落错人），规格边界按"仅师傅本人提交"理解。
