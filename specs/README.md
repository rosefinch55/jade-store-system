# 开发规格文档

按功能域拆分，每个 feature 一套四份文档。开发按这里的顺序推进，代码以文档为准。

## 为什么拆成这些文档

| 文档 | 回答什么 | 谁看 |
|---|---|---|
| `spec.md` | 这个功能要做什么、什么算做对 | 开发前对齐范围，验收时逐条比对 |
| `data-model.md` | 涉及哪些表、字段什么含义、校验规则落在哪 | 建表与写实体类 |
| `contracts/api.md` | 前后端之间的接口约定 | 前后端并行开发，联调时对照 |
| `tasks.md` | 拆到可执行的任务，带验收标准 | 排期与自检 |

需求细节以分析设计报告的 28 条用例规约为准，这里不复述，只做开发视角的转写：把规约的「基本路径 + 扩展 + 字段列表 + 业务规则」翻译成接口、表操作和任务。

## 开发顺序

```
000-base ──→ 001-goods ──→ 002-sale ──→ 004-transfer
                    │              └──→ 005-consign
                    ├──→ 003-customer
                    └──→ 006-processing
```

先做 `000-base` 和 `001-goods`，这两块跑通就有了登录和货品档案。`002-sale` 完成后系统能演示核心闭环：登录 → 建档 → 成交 → 看统计。

`003-customer`、`004-transfer`、`005-consign`、`006-processing` 可以并行，也可以按时间取舍——课程演示不要求 28 个用例全上，但核心链路缺一不可。

## 通用约定

所有 feature 共用以下约定，各 `contracts/api.md` 不再重复：

- **路径前缀** `/api`，风格 REST：路径用名词，动作交给 HTTP 方法
- **响应包装** `{ "code": 0, "message": "ok", "data": {} }`
- **错误码** 400 参数错、401 未登录、403 账号停用或无权限、404 不存在、409 状态冲突、422 业务规则不满足、**423 账号锁定**（登录连续 5 次错误）、500 服务端异常
- **健康检查** `GET /api/health` 各 feature 共用，返回 200 即视为可用，不重复定义
- **分页** 请求 `page`（从 1 起）、`size`（默认 20，上限 100），响应 `{ total, page, size, items }`
- **时间格式** `yyyy-MM-dd HH:mm:ss`，时区 `Asia/Shanghai`
- **鉴权** 登录后下发 token，请求头 `Authorization: Bearer <token>`；权限点按报告 §4.4 矩阵
- **不允许直接改状态** 货品、订单等对象的状态变更一律由业务动作驱动，不开放通用 status 接口

## 与后端约定的技术栈

SpringBoot 3 + MyBatis-Plus + MySQL 8.0，分层 Controller / Service / Mapper，业务规则只写在 Service。

契约本身与框架无关，换实现不用改文档。
