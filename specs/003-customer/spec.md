# 功能规格：客户与到店

**功能分支**：`003-customer`
**需求来源**：分析设计文档 §2.3 UC-04 维护客户信息、UC-09 浏览货品、UC-10 预约查看货品、UC-13 预定商品、UC-27 查询预约、UC-28 跟进预定到店
**依赖**：`000-base`（权限）、`001-goods`（货品展示范围）
**状态**：Draft

## 范围

客户档案维护、小程序端免登录浏览、看货预约与查询、商品预定与额度控制、销售端跟进到店。

上门预约（UC-15）属 `006-processing`，不在本处。

## 关键区分：预约与预定是两件事

| | 预约（UC-10） | 预定（UC-13） |
|---|---|---|
| 表 | `t_reservation` | `t_booking` |
| 目的 | 约好时间来店看货 | 把货留住，到店有货可看 |
| 是否锁货 | 不锁，货品状态不变 | 不锁，但同货品只能 1 条有效预定 |
| 额度限制 | 无 | 一个手机号最多 3 条 |
| 编号前缀 | `YY` | `YD` |

两者都免登录，靠手机号识别。

## 性能与约束

- 客户查询（任一条件）3 秒内反馈（UC-04）
- 货品图片加载 2 秒内完成（UC-09）
- 预约与预定提交后 1 秒内反馈（UC-10、UC-13）
- 预约查询 2 秒内返回（UC-27）
- 不做短信/微信推送、会员等级、积分、优惠券、客户画像打分（UC-04 设计约束）
- 手机号后四位只作检索条件，不作身份凭据（UC-27 设计约束）

## 边界情况

- 客户改名不改编号，历史成交仍指向同一客户（FR-002）
- 一个客户可同时有多条预定额度，额度和预约数量无关
- 预定取消：客户主动取消（状态「已取消」）不释放额度，与爽约同处理
- 同一手机号既是客户又提交预定，`t_booking.customer_id` 按手机号自动关联，关联不上时留空
- 货品被预定期间若被现场客户看中，销售需先取消预定才能成交；系统不强制锁定

## 与文档的差异

**一、「允许展示」缺字段**

UC-09 前置条件写「状态为在柜**且允许展示**」，但 `t_goods` 没有控制展示开关的字段。当前按「状态=在柜」处理，即所有在柜货品都展示。

若需要单独控制（比如某些高货不对外展示），得加 `show_in_album TINYINT(1)`，届时走一次 schema 变更。

**二、预定额度的「同时占用」判定**

UC-13 说「最多同时占用 3 条」，但没说哪几种状态算「占用」。从业务规则②③⑤反推：待到店、已联系、已爽约都占额度，只有已达成释放。已取消按③「不释放」处理，也占。

所以有效占用 = `status IN ('待到店','已联系','已爽约','已取消')`。这个口径写在 `data-model.md` 的额度计算里，实现时按这个来。

**补充（2026-10-26 复核，对应代码审查报告 §三 B 组）**

B4｜预定"已取消"不可达。规格 FR-021 允许客户主动取消，实现没有任何取消入口，该状态永远进不去。处置：接受现状，改期与取消都走人工；若补，加一个按手机号后四位查单再取消的接口。

B5｜超时未到店不自动爽约。规格 FR-023 要求自动，实现靠店员人工标记，且 `t_booking` 没有约定到店时间字段。处置：接受现状，口径改为"人工标记"；要自动化得先补到店时间字段。

B6｜预定跟进只有计数没有面板。接口齐（联系、到店结论），柜台端只显示概览数字。处置：标注为未完成，属增强项。

B17｜"今日名单"按提交时间过滤，不是到店时间。与 B5 同源（没有到店时间字段）。处置：接受现状，名单含义改为"今天新提交的预定"；补字段后可切回到店时间。
